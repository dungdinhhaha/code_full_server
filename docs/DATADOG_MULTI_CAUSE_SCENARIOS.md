# Datadog Level 5 story: EC2 keeps the farm's harvest decision trustworthy

## The story

The EC2 instance is the farm's control room: it runs the SMIOT app, MQTT broker, MongoDB, the cloud-device bridge, and the Datadog Agent. If one server component fails, the dashboard may still open while new sensor data stops being stored. That can make the melon GDD and predicted harvest window stale, and can leave irrigation decisions based on old readings.

The demo follows one business question: **Can SMIOT keep the harvest forecast and irrigation decision trustworthy when part of its server fails?** Datadog detects the impact, Bits investigates which EC2 component caused it, an allowlisted recovery action handles only that component when checks pass, and a verifier proves the service and fresh MongoDB data have returned. When evidence does not support a safe restart, automation refuses and reports why.

This is a simulated farm data path running on the real EC2 server. The claims concern server and application recovery; they do not claim a physical sensor or pump was repaired.

## What makes this Level 5 in the transcript's sense

The transcript uses “Level 5” for a Bits Investigation-led autonomous loop, not a Datadog product-wide maturity score. The demo must show all of these in one incident:

1. **Detect:** a monitor alerts on an operational symptom before a stale harvest estimate is trusted.
2. **Investigate:** Bits automatically starts from the monitor alert, forms competing hypotheses, and checks host metrics, structured logs, APM traces, dependency health, and MongoDB freshness.
3. **Choose safely:** recovery is deterministic and allowlisted. Bits provides the diagnosis; it does not get unrestricted shell access. The action runs only when its preconditions match the diagnosed service.
4. **Refuse the wrong fix:** if Mongo is healthy but the bridge is down, the action must not restart Mongo. If disk is full or evidence conflicts, automation refuses and escalates.
5. **Prove recovery:** check systemd state, application health, MQTT connectivity, MongoDB ping, a newly persisted time-series sample, and Datadog monitor recovery. Save the same incident ID, action result, and recovery evidence.

## Current automation boundary

- The EC2 systemd integration is now configured in `scripts/aws/bootstrap_ubuntu.sh` and deployed through SSM. Datadog has reported the app, MongoDB, Mosquitto, Nginx, bridge, and Agent units as active; the observed restart counts were zero.
- Datadog monitor **340356283** watches `systemd.unit.active{host:i-00bf2d3591d3ee0a2,unit:smiot.service}` and is P2. Automatic Bits investigation is enabled. It currently has no notification recipient, so it updates monitor state and can trigger Bits but does not page a person.
- Automatic Bits investigation was previously enabled on the MongoDB, MQTT, and stale-telemetry monitors. Verify these settings again in the UI before claiming a new org-wide state.
- AWS SSM document `SMIOT-GuardedStartApp` is Active. It accepts only an incident identifier and a `DryRun` switch, checks the root-disk threshold plus `mongod.service` and `mosquitto.service`, and can start only `smiot.service`. After a real start it checks `/login` and requires a newer, recent MongoDB telemetry timestamp. The document never restarts MongoDB or MQTT.
- AWS role `DatadogSMIOTServiceRecoveryRole` was created with `ssm:SendCommand` scoped to that document and the target EC2 instance; readback permissions are limited to SSM command invocation results. Datadog's connection page displays the required Actions principal and external-ID condition, but the current AWS CLI identity check hangs, so the role's saved trust policy has not yet been read back and matched against the connection.
- A CLI SSM `DryRun=true` invocation completed with `Success` and returned `app_already_active`. This confirms the document can execute against the managed instance and correctly avoids starting an already-active app. It **does not** prove Datadog can assume the role, that the Mongo readback check passed, or that an outage was repaired.
- The published Datadog workflow **SMIOT EC2 Guarded Web Recovery** uses the EC2 Agent Private Action Runner and the predefined action `recover-smiot-web`, targeting only EC2 `i-00bf2d3591d3ee0a2`. It does not depend on the separate AWS role connection, whose `sts:AssumeRole` check had failed.
- On 2026-11-04 the runner's on-host script was changed from blind `systemctl restart` to guarded behavior. It no-ops when HTTP is healthy; if the app process is active but HTTP fails, it records the dependency/disk state and refuses to restart; it will run only `systemctl start smiot.service` when the app is stopped/failed, root disk is below 85%, MongoDB and Mosquitto are active, and MongoDB readback succeeds. It uses a lock and five-minute cooldown.
- The `dd-agent` sudo grant allows only `systemctl start smiot.service` and the root-owned, no-argument MongoDB readback helper. The helper reads the protected app credentials internally and returns only the newest telemetry timestamp. The predefined script remains fixed to `/usr/local/sbin/smiot-recover-guarded`; it accepts no arbitrary shell command or service name.
- Live no-op proof on 2026-11-04: the Datadog workflow manual run completed successfully after the change; direct runs as `dd-agent` emitted `action=none`, `result=verified_healthy`, `reason=already_healthy`. Sudoers validation passed, the app unit remained `active`, and the local login endpoint returned HTTP 200. The JSONL recovery file was added to the Agent log config and the event was retrieved from Datadog US1 with source `smiot-recovery`. No service was restarted or started during this check.
- Current limit: the stopped-app `systemctl start` branch has not been exercised, because doing so requires a controlled interruption. Thus the safe no-op path and workflow-to-runner connection are proven, while automatic start + fresh MongoDB telemetry + trace + monitor recovery still require a controlled recovery drill. Do not claim full outage/recovery proof yet.
- No server service has been deliberately stopped. A controlled outage/recovery drill is still required to prove the final loop; keep it separate from normal production operation and run it only when explicitly authorized.
- Keep one fault active at a time. Give each run a unique incident ID; attach it to structured logs, traces, MongoDB incident/action records, and workflow execution. Do not put incident IDs in metric tags.
- Connect a harvest lot only if the farm/node assignment is valid at the incident timestamp. A server-wide outage must not be assigned to an arbitrary lot.

## Demo order

1. Start at the Datadog EC2 host view and SMIOT service dashboard. State the business risk: a live page is not proof that fresh data is being stored.
2. Open a pre-recorded app/bridge/Mongo incident and let Bits compare the hypotheses. Keep the other services healthy so the evidence distinguishes one root cause.
3. Show the selected service, the guarded action and its idempotency/cooldown result.
4. Follow one incident ID through alert, log, trace, action ledger and recovery checks.
5. Show the newest MongoDB Time Series sample and the recovered monitor. If any check fails, leave the incident open and show the refusal reason.
